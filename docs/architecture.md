# 架构与节点顺序

## 摄入图

```
fetch → normalize → rank → summarize → embed → dedupe → deliver → store
```

状态里除 `articles` 之外都用累加型 reducer：`dropped`、`warnings` 和 `stats` 由多个节点
各写各的，后写的不能覆盖先写的。`articles` 用整体替换，每个节点输出自己这一轮的完整列表。

依赖（Redis 连接、编码器、摘要器）通过工厂函数注入节点，不放进 state。state 会进
checkpoint，把连接对象写进去既不能序列化，恢复时也会拿到一个过期连接。

## 为什么是这个顺序

**· normalize 必须早于 summarize**

OpenAI Blog 的 feed 是全量归档，一次返回约 1255 条。三条源合计单次抓取约 1295 条，
而每天真正新增的通常只有十几条。normalize 里的历史过滤不花钱，放在模型调用之前，
摘要对象从 1295 条降到 15 条（受 TOP_N 限制），模型成本相差约两个数量级。

**· rank 必须早于 summarize**

三个源的产量差两个数量级，只按权重排序会让产量大的源占满候选。rank 先给每个源留出
`MIN_PER_SOURCE` 条保底名额，再补足到 `TOP_N` 条上限。

**· embed 排在 summarize 之后**

embed 的输入是「中文标题加中文摘要」，不是英文原文。中英文两条讲同一件事的资讯在摘要
这一步被拉进同一个语言空间，向量距离才有意义。直接对英文原文编码时，跨语言同事件的
相似度只有 0.07 至 0.30，判不出来。

**· store 必须晚于 deliver**

图文上是一条条件边：`deliver` 之后判断 `delivered`，为真才走 `store`，否则直接结束。

这条边来自第一版的教训。Dify 的 HTTP 节点只看状态码，推送接口业务失败时仍然返回 200，
工作流显示成功、历史却被写脏，第二天那些内容被当成已处理而永远消失。把「送达」作为
写历史的唯一前置条件，是这个问题的通用解。

## 失败时的行为

每个外部依赖失败时的取舍都是明确的，不是默认值。

**· 单个源抓取失败**

记一条警告并继续，其他源照常产出。缺失源在统计里记为 0，日报里会体现为条数减少。

**· Redis 查询失败（历史过滤）**

跳过历史过滤，条目照常往下走。宁可当天多推两条重复，也不要因为存储故障把日报清空。

**· 摘要失败**

整批降级为「原标题加原文片段加来源权重折算的评分」，保底渲染仍然产出一份朴素日报。

**· 编码失败**

跳过语义去重，所有条目放行。没有向量的条目在写回阶段仍然会写 `seen:` 键，
URL 级去重不受影响。

**· 没有新条目**

不产出日报、不写历史，运行日志里记为 delivered 为 false。

## 查询图

```
embedQuestion → search → compose
```

search 走混合检索：时间范围过滤加 KNN 向量检索。过滤条件写在 KNN 之前，
需要 `DIALECT 2`，否则是取完 KNN 再过滤，限定时间范围后经常返回不满 k 条。

向量检索失败或没有命中时退回「按时间取最近若干条」，保证查询有返回而不是空手而归。
